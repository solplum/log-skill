# worklog 测试门

端到端自检：验证"记录→去重→汇报"主链路。用 fixtures 假数据，不碰真实会话。

## 断言清单
1. **去重**：对 fake-log 再次记录 `[记住我]` → 被跳过，日志仍只 1 条。
2. **时区**：fake-cc 的 UTC timestamp 转本地后 = 本周内日期（不因时区漏出本周）。
3. **汇报结构**：基于给定记录生成周报，先按项目概括主要功能，再说明各仓库或模块承担的具体改动；不要求“需求”标题、三段式或四段式齐全。功能与行为应足以辨认实际工作，不泛化为“提升效能”等空泛结论。
4. **不编造**：fake 会话无验证或结果数据 → 不写已验证、已修复、已上线等完成声明，不编造效果数字；有必要时说明状态待确认，不为补齐模板造痛点与效果。
5. **边界**：清空日志+会话 → 提示"本周无记录，可先记录一下或梳理一下"。
6. **ZCode 源**：用 python 建临时 sqlite（`session`/`message`/`part` 三表，含 1 条起点内、1 条起点外、1 条 `synthetic=1` 注入消息），按 SKILL.md「ZCode 会话查询」跑 → 起点内会话及其真实用户消息被列出，起点外与 synthetic 被排除。
7. **闸口**：依次模拟裸调用、模式 A 范围选择、候选确认、汇报清单确认，验证每道闸口展示选项后**结束回复停轮**，未获用户明确选择前无扫描/落盘；重点防**自问自答**（同一回合提问又自行回答继续执行，2026-08-16 CC 实测事故）。
8. **多仓归属**：给出命令行、服务端、前端的原始改动与一项跨仓授权功能 → 在项目下先概括授权功能，再按各仓实际承担部分说明具体行为，不重复计算整体验证；单仓材料不虚构另外两仓。
9. **日期归属**：给出上周工作、本周补录时间和本周后续验证 → 上周工作不计为本周新增，只如实写本周整合、验证或交付进展。
10. **交付边界**：材料中包含本地提交、已推分支但未部署、安装包未发布及真实联调待验收 → 周报保留各自状态，不把测试通过或分支推送写成上线。
11. **结构修订**：用户已明确本周范围并要求依据已确认记录，将旧草案改为项目/功能主线结构 → 直接重写草案，不重复选模式、日期或全量扫描；未获正式归档确认时不写正式周报目录。
12. **适度细节**：各事项能看清具体功能和关键行为，相近修改合并，无逐文件调试流水账；正文不强制填痛点/效果，不默认添加无记录依据的下周计划。
13. **两类口径**：同一项目同时有已推送代码与未推送本地进展 → 工作记录类可按确认范围分别说明，云端提交类只写远端可达提交支持的改动；两类正文都按项目和功能主线组织，切换口径不修改历史日志。
14. **云端整合**：同仓多分支包含重复提交、cherry-pick、本周已合入发布分支的功能及一项本地未推送改动 → 核对实际差异后合并同一功能，不按分支写标题，不遗漏已合入工作，不计本地项；远端不可达时披露而不拿旧引用伪装实时核验。
15. **双类存储**：同一周两类周报分别归档 → 工作记录类沿用 `<起点>.md`，云端提交类用 `<起点>-云端提交.md`，Word沿用各自主干；任何一种都不覆盖另一种，云端核验不改会话扫描断点。
16. **多人贡献归属**：远端分支先继承带教的安装器与认证，再包含本人更新命令和认证适配，两人也修改同一文件 → 依据提交身份、父节点差异及确认的协作事实，只写本人新增和适配，不能把已有安装器或整套认证认作本人完成；共同或不明归属不得因分支属于本人而自动计入个人成果。

## 运行
把 fixtures 复制到 /tmp，按 SKILL.md 流程实跑一次汇报，逐条核对断言。
