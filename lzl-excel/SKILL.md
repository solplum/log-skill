# lzl-excel

将指定范围内的代码与工程改动整理为符合带教/评审终审标准的**在线电子表格**（飞书表格、腾讯文档等）。

表格面向直接提交与跨端评审，结构严谨、证据闭环、排版精细。

---

## 核心铁律（硬红线）

1. **严格范围只读，绝不擅自线上测量**：
   - 只能在**用户指定的范围**（当前会话、指定本地 Git diff/commit、明确提供的测试日志或设计文档）内读取；
   - **“有就有，没有就没有”**：有客观记录就提炼写入，没有记录就如实标注（如 `无记录`），**绝对禁止**擅自向外部或生产环境发起网络请求、curl 探针或浏览器访问去测延迟、测接口或看页面。
2. **严重缺失主动提问门（Question Gate）**：
   - 当原背景严重缺失、改动无法归因、或关键验证结论完全空白且无法从证据推导时，**必须暂停并向用户提出具体问题**，由用户补充或确认，绝不自行脑补或捏造。
3. **列职责彻底解耦（Column Discipline Gate）**：
   - `问题确认` 列只答**“病存在吗、在哪、怎么确认的”**（病）；
   - **严禁在“问题确认”中出现任何“修复后”、“优化后”或修复效果描述**；
   - 彻底废除外层 `已确认（...）` 包裹语法，统一采用裸前缀（如 `本地：...`、`线上：...`）；
   - 双地点必须分行写明 `本地：...` 换行 `线上：...`，**严禁使用“都有”**；
   - 纯新增能力统一填 `无历史问题（新增能力）`，严禁写“不适用”。
4. **原背景与本次改动 1:1 编号换行严格对齐（Pairing Gate）**：
   - 多事项行：`原背景/问题` 必须使用 `1、` `2、` `3、` 编号且**单元格内强制换行**；
   - `本次实际改动` 必须使用完全相同的序号数量、相同顺序**逐条对齐解答**，两个大格内的事项数量必须绝对相等，严禁错位；
   - 单事项行：直接一句话客观陈述，不带编号，避免为编号而编号。
5. **提交即终稿（Submission-Ready Gate）**：
   - 绝不出现“会话记录中未发现”、“AI对话”、“worktree 起服”、“验证矩阵第 X 项”等开发过程私有黑话；
   - 绝不使用“同上”、“如前所述”等上下文依赖指代；
   - 数字、退出码、端口号、版本号在交付前必须对着范围证据严格复核。
6. **多仓库多 Sheet 与精细排版**：
   - 多个仓库/子系统强制拆分为独立的 Sheet（如 `cluster-cli`、`cluster-dashboard-server`、`cluster-dashboard-web`）；
   - 所有 Sheet 首行冻结、全局开启自动换行、表头深色底白字加粗；
   - 若用户需要“变更日志”，作为独立 Sheet 采用文档式排版（隐藏网格线、日期大标题**加粗居中**、圆点列表内容左对齐）。

## 工作流（Workflow）

### 第一步：范围界定与被动证据读取
1. 确定本次表格的覆盖范围：
   - 涉及哪些仓库或模块？
   - 统计范围是本次会话、指定 commit，还是指定分支 diff？
2. 在用户指定范围内读取证据：
   - 读 Git diff / log 确认实际发生的改动文件与行为；
   - 读会话中已记录的本地/线上测试输出、构建结果与退出码；
   - 严禁触发任何对外部/生产环境的网络探测。

### 第二步：信息完整性检查与提问门禁
扫描提炼后的数据矩阵：
- 是否存在改动事项不知道当初为什么改（原背景缺失）？
- 是否存在核心修复没有任何验证结果记录？
- 是否存在模块划分不清或归属存疑？

**若存在严重缺失**：整理为清单向用户提问（使用清晰的单选或简短问答），待用户确认后再继续。

### 第三步：格式与门禁自检（8 列模型）
对每一行数据严格执行校验：

| 列名 | 纪律要求 |
|:---|:---|
| **序号** | 连续数字，1 开始。 |
| **改动事项** | 短名词短语，按业务类型归纳（如 `外链安全过滤与断网容错`、`UI 优化`）。 |
| **模块** | `<业务模块>[ · <端>]`，短码优先（如 `cli`、`web 前端`、`server 后端`）。无端属性不带后缀。 |
| **问题确认** | **只写病**。裸前缀（`本地：...` / `线上：...`）。双地点分行，禁止“都有”。纯新增填 `无历史问题（新增能力）`。无修复描述。 |
| **原背景/问题** | 以前的状态与缺陷。多条必须带 `1、` `2、` 编号且单元格内换行。 |
| **本次实际改动** | 现在的转变。与原背景**数量相等、编号一致、1:1 顺序配对换行**。 |
| **交付状态** | 严格三值之一：`未上传` / `已上传` / `已部署`。 |
| **验证结果** | 前缀：`本地：` / `线上：` / `通过线上API：`。只填已有硬数据（退出码、耗时、数据量、测试数）。 |
| **表外注** | 表格底部独立行：`表外注：<事项>（<简述>）<状态与待办>`。用于已确认未修复或表外遗留问题。 |

### 第四步：在线平台渲染落盘
根据目标平台调用对应适配器：
1. **飞书表格（Feishu / Lark Sheets）**：
   - 参考 `references/feishu-adapter.md`；
   - 优先检测 `@larksuite/cli`（若需授权引导用户，或使用飞书 API / Webhook）；
   - 写入多 Sheet，设置样式（深蓝表头 `#1F2329` / `#245BDB`、首行冻结、自动换行、行高列宽）；
   - 若含“变更日志”页：隐藏网格线，日期居中，条目左对齐。
2. **腾讯文档（Tencent Docs）**：
   - 参考 `references/tencent-adapter.md`；
   - 支持通过腾讯文档开放 API、结构化剪贴板导入或自动化助手写入对应多 Sheet 与样式。
3. **本地备用降级（Markdown / HTML / PNG）**：
   - 若在线凭据未就绪，输出标准 GFM 表格或生成符合样式的 HTML/PNG 供临时使用。

### 第五步：交付与用户验收
- 输出最终生成的在线文档链接；
- 附带一份简洁的“变化点/关键确认项汇总”；
- 询问用户是否有需要增删调整的行。
